# Gestion Club V1.26 — Start Dev

## Principe

V1.26 démarre exclusivement depuis **V1.25.13.17**, version stable et fonctionnelle validée.

Le premier objectif de V1.26 est de rendre le stockage compréhensible, sûr, segmenté et prêt pour le multi-club sans casser les fonctions validées de V1.25.13.17.

## Décision d'architecture validée

La V1.26 utilisera **plusieurs fichiers physiques de données**.

Ces fichiers seront stockés sur la machine Windows qui héberge le serveur Gestion Club, dans une arborescence persistante séparée du code applicatif.

### Périmètre V1.26

- développement sous Windows ;
- serveur Gestion Club exécuté sous Windows ;
- fichiers de données stockés sur le disque de la machine Windows serveur ;
- séparation physique entre programme et données ;
- chemins de données configurables ;
- aucune contrainte d'architecture liée à NeoOS dans V1.26.

**NeoOS est hors périmètre de conception de V1.26.** Si Gestion Club doit être hébergé plus tard sur NeoOS, ce sera à NeoOS de s'adapter pour exécuter le serveur et héberger l'arborescence de fichiers définie par Gestion Club.

## Problème à résoudre

La logique actuelle de stockage n'est pas encore suffisamment claire pour garantir :

- l'absence de mélange entre clubs ;
- la cohérence entre licences, personnes, comptes, rôles et équipes ;
- une restauration partielle sans perte globale ;
- une synchronisation sûre entre licences et comptes serveur ;
- l'exploitation de plusieurs centaines de comptes ;
- une architecture multi-club ;
- la protection contre l'écrasement d'un fichier monolithique unique.

## Architecture physique cible

Exemple conceptuel sous Windows :

```text
D:\GestionClub\
├── app\                         # programme / serveur / client
├── data\                        # données persistantes hors code
│   ├── instance\
│   │   ├── instance.db
│   │   ├── accounts.db
│   │   ├── permissions.db
│   │   └── audit.db
│   ├── clubs\
│   │   ├── <club_id_1>\
│   │   │   ├── club.db
│   │   │   ├── people.db
│   │   │   ├── licenses.db
│   │   │   ├── teams.db
│   │   │   ├── memberships.db
│   │   │   ├── documents\
│   │   │   └── settings.db
│   │   └── <club_id_2>\
│   │       └── ...
│   ├── sync\
│   ├── imports\
│   ├── exports\
│   └── backups\
└── logs\
```

Cette arborescence est une cible de conception. Les noms exacts des fichiers seront figés après inventaire des accès réels de V1.25.13.17.

## Principes obligatoires

1. **Pas de fichier data unique global** contenant tout l'état de Gestion Club.
2. **Séparation code / données** : une mise à jour du programme ne doit jamais remplacer les données persistantes.
3. **Séparation instance / club** : les données techniques globales ne doivent pas être mélangées aux données métier d'un club.
4. **Séparation par domaine** : comptes, licences, personnes, équipes, permissions, audit et documents doivent être isolés de façon contrôlée.
5. **Contexte club explicite** : toute donnée métier doit être rattachée à un `club_id` stable.
6. **Chemins configurables sous Windows** : aucune donnée persistante ne doit dépendre d'un chemin codé en dur dans la logique métier.
7. **Intégrité des écritures** : éviter les fichiers partiellement écrits et sauvegarder avant migration.
8. **Restauration sélective** : permettre de restaurer un club ou un domaine sans écraser toute l'instance lorsque cela est sûr.

## Niveau 1 — instance

Une installation Gestion Club contient une instance technique et peut gérer un ou plusieurs clubs.

Les données globales peuvent contenir notamment :

- configuration serveur ;
- index des clubs ;
- comptes et rôles globaux si nécessaire ;
- permissions ;
- journal d'audit ;
- versions de schéma ;
- catalogue des sauvegardes.

## Niveau 2 — club

Chaque club possède son propre répertoire physique sous `data/clubs/<club_id>/`.

Chaque donnée métier doit être rattachée à un `club_id` stable.

Aucune licence, personne, équipe, adhésion, document métier ou rôle local ne doit être résolu sans contexte de club explicite.

## Niveau 3 — domaines

Séparer au minimum :

- `clubs`
- `people`
- `licenses`
- `accounts`
- `roles_permissions`
- `teams`
- `memberships`
- `documents`
- `settings`
- `audit`
- `backups`
- `sync`

La répartition finale entre fichiers physiques sera validée après inventaire du stockage V1.25.13.17.

## Identifiants canoniques à définir

- `club_id`
- `person_id`
- `license_id`
- `account_id`
- `team_id`
- `membership_id`

Un numéro de licence, un nom ou un identifiant de connexion ne doit pas servir à lui seul de clé technique universelle.

## Licences -> comptes serveur

La synchronisation doit être idempotente : relancer la synchronisation ne doit pas recréer les mêmes comptes ni modifier silencieusement un compte existant.

Avant validation, classer chaque fiche dans un des états :

- compte existant et correctement lié ;
- compte manquant à créer ;
- doublon potentiel ;
- fiche incomplète ;
- conflit d'identité ;
- conflit de club ;
- compte désactivé ;
- liaison à confirmer.

La création automatique intervient uniquement pour les lignes sans ambiguïté.

## Écran Comptes & permissions

Cible : gestion confortable d'au moins 300 comptes.

Onglets :

- Administrateurs
- Éducateurs
- Licenciés
- Comptes incomplets
- Comptes désactivés

Fonctions minimales :

- recherche nom ;
- recherche prénom ;
- recherche numéro de licence ;
- recherche identifiant ;
- tri des colonnes ;
- filtres rôle ;
- filtres catégorie ;
- filtres équipe ;
- filtres statut ;
- filtre fiche liée/non liée ;
- actions groupées ;
- aperçu des anomalies avant validation.

## Sauvegarde

La stratégie cible doit permettre :

- sauvegarde complète de l'instance ;
- restauration complète ;
- sauvegarde par club ;
- restauration par club ;
- sauvegarde contrôlée par domaine lorsque cela est sûr ;
- historique et migrations de schéma ;
- contrôle d'intégrité ;
- vérification avant écrasement ;
- rollback de migration.
