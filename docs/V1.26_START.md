# Gestion Club V1.26 — Start Dev

## Principe

V1.26 démarre exclusivement depuis **V1.25.13.17**, version stable et fonctionnelle validée.

Le but de V1.26 n'est pas d'ajouter immédiatement de nouvelles fonctions visibles : le premier bloc doit rendre la base de données compréhensible, sûre, segmentée et prête pour le multi-club.

## Problème à résoudre

La logique actuelle de stockage n'est pas encore suffisamment claire pour garantir à long terme :

- l'absence de mélange entre clubs ;
- la cohérence entre licences, personnes, comptes, rôles et équipes ;
- une restauration partielle sans perte globale ;
- une synchronisation sûre entre licences et comptes serveur ;
- l'exploitation de plusieurs centaines de comptes ;
- une future architecture multi-club.

## Architecture cible — première définition

### Niveau 1 — instance

Une installation Gestion Club contient une instance technique et peut gérer un ou plusieurs clubs.

### Niveau 2 — club

Chaque donnée métier doit être rattachée à un `club_id` stable.

Aucune licence, personne, équipe, compte, rôle métier ou document métier ne doit être résolu sans contexte de club explicite, sauf données techniques globales strictement identifiées.

### Niveau 3 — domaines

Séparer au minimum :

- `clubs`
- `people`
- `licenses`
- `accounts`
- `roles_permissions`
- `teams`
- `memberships`
- `documents`
- `settings`
- `audit`
- `backups`
- `sync`

Le détail des tables sera validé après inventaire du schéma V1.25.13.17.

## Identifiants canoniques à définir

- `club_id`
- `person_id`
- `license_id`
- `account_id`
- `team_id`
- `membership_id`

Un numéro de licence, un nom ou un identifiant de connexion ne doit pas servir à lui seul de clé technique universelle.

## Licences -> comptes serveur

La synchronisation doit être idempotente : relancer la synchronisation ne doit pas recréer les mêmes comptes ni modifier silencieusement un compte existant.

Avant validation, classer chaque fiche dans un des états :

- compte existant et correctement lié ;
- compte manquant à créer ;
- doublon potentiel ;
- fiche incomplète ;
- conflit d'identité ;
- conflit de club ;
- compte désactivé ;
- liaison à confirmer.

La création automatique intervient uniquement pour les lignes sans ambiguïté.

## Écran Comptes & permissions

Cible : gestion confortable d'au moins 300 comptes.

Onglets :

- Administrateurs
- Éducateurs
- Licenciés
- Comptes incomplets
- Comptes désactivés

Fonctions minimales :

- recherche nom ;
- recherche prénom ;
- recherche numéro de licence ;
- recherche identifiant ;
- tri des colonnes ;
- filtres rôle ;
- filtres catégorie ;
- filtres équipe ;
- filtres statut ;
- filtre fiche liée/non liée ;
- actions groupées ;
- aperçu des anomalies avant validation.

## Sauvegarde

La V1.26 doit supprimer le risque conceptuel d'un stockage monolithique unique dont l'écrasement entraîne la perte de tout l'état.

La stratégie cible doit permettre :

- sauvegarde complète ;
- restauration complète ;
- sauvegarde par club ;
- export contrôlé par domaine si pertinent ;
- historique/migrations de schéma ;
- contrôle d'intégrité ;
- vérification avant écrasement ;
- rollback de migration.

Le découpage physique exact (une base SQLite avec séparation logique ou plusieurs fichiers contrôlés) n'est **pas encore décidé**. Il doit être choisi après inventaire des accès existants afin de ne pas introduire une complexité ou des risques inutiles.

## Étapes V1.26

### V1.26.0 — inventaire

- Cartographier SQLite, JSON, snapshots, fichiers `data/` et données navigateur encore utilisées.
- Identifier les écritures et lectures réelles.
- Identifier les clés utilisées aujourd'hui.
- Identifier les dépendances de sauvegarde/restauration.

### V1.26.1 — modèle canonique

- Définir les entités.
- Définir les clés et relations.
- Définir les contraintes d'unicité par club.
- Définir les statuts et règles de suppression/désactivation.

### V1.26.2 — stratégie multi-club

- Introduire le contexte `club_id`.
- Définir le club actif.
- Interdire les lectures/écritures croisées.
- Tester deux clubs contenant des noms et numéros potentiellement similaires.

### V1.26.3 — migration et sauvegarde

- Migration non destructive depuis V1.25.13.17.
- Backup avant migration.
- Validation d'intégrité après migration.
- Rollback documenté et testé.

### V1.26.4 — synchronisation licences/comptes

- Analyse à blanc.
- Détection des comptes manquants.
- Détection des doublons et conflits.
- Création idempotente des comptes validés.
- Même pipeline pour éducateurs et licenciés.

### V1.26.5 — Comptes & permissions

- Nouvelle vue adaptée à 300+ comptes.
- Onglets, recherche, filtres, tri.
- Actions groupées sécurisées.
- Fiches liées et anomalies visibles.

### V1.26.6 — stabilisation

- Tests migration.
- Tests multi-club.
- Tests permissions.
- Tests sauvegarde/restauration.
- Tests Windows et serveur.
- Vérification de non-régression de V1.25.13.17.

## Décision différée

Ne pas traiter DynDNS, serveur public ou exposition Internet avant validation de ce cycle.
