# V1.26.0 — Inventaire réel V1.25.13.17

## Référence auditée

L'inventaire a été complété à partir de :

- l'archive fonctionnelle `GestionClub_V1.25.13.17_Windows_test_bandeau_admin` ;
- la copie du dossier d'installation Windows actif ;
- une copie du dossier `data` fournie pour audit local uniquement.

**Aucune donnée réelle du club, aucun fichier SQLite, aucun hash de mot de passe, aucun token de session, aucun PDF réel et aucune sauvegarde complète n'est destiné au dépôt GitHub.**

La base fonctionnelle officielle reste **V1.25.13.17**. La V1.26 part de cette version sans modifier son comportement avant migration contrôlée.

## 11. Redondances confirmées

### Licenciés

Une même fiche peut exister dans :

1. `localStorage -> state.members` ;
2. backup JSON ;
3. `revisions.payload` ;
4. table `members` ;
5. colonne `members.payload`.

### Équipes

Même duplication via :

1. `state.teams` ;
2. backup ;
3. `revisions.payload` ;
4. table `teams` ;
5. `teams.payload`.

### Comptes

Deux systèmes coexistent :

- `state.accounts` côté Manager ;
- `users` + `user_profiles` côté serveur.

La V1.26 devra définir une seule relation canonique entre personne, licence et compte.

## 12. Différence entre le dépôt précédent et l'archive finale

L'audit a confirmé que le dépôt GitHub utilisé au démarrage de V1.26 possédait encore un `server.py` ancien d'environ 26 Ko, alors que l'archive finale V1.25.13.17 contient un `server.py` d'environ 52 Ko.

Les fonctionnalités manquantes dans l'ancienne copie GitHub comprennent notamment :

- rôles `educator` et `member` ;
- table `user_profiles` ;
- permissions serveur ;
- rattachement compte / licencié ;
- périmètre éducateur ;
- restrictions d'API selon le profil ;
- gestion serveur des comptes ;
- logique de portail serveur plus récente ;
- restrictions du bandeau serveur selon le profil.

Les sources V1.25.13.17 non sensibles doivent donc être utilisées comme **référence de restauration du code** avant le développement de la nouvelle persistance.

## 15. Conclusion V1.26.0

L'inventaire V1.25.13.17 est maintenant suffisamment précis pour fermer la phase V1.26.0.

Le problème principal n'est pas l'absence de données : c'est l'absence d'une **source de vérité unique et explicitement structurée**. La V1.26 devra remplacer progressivement le couple `localStorage + snapshot JSON monolithique + projections SQLite` par plusieurs fichiers physiques serveur avec responsabilités séparées et migration non destructive.

Prochaine phase : **V1.26.1 — conception du modèle physique et des identifiants canoniques**, sans encore supprimer ni convertir les données V1.25.13.17.
