# V1.26.0 — Inventaire réel des données de la base V1.25.13.x

## Statut

Inventaire technique de départ pour V1.26.

Base fonctionnelle officielle : **V1.25.13.17**.
Cible d'exécution : **Windows**.
Décision V1.26 : les données seront à terme réparties dans **plusieurs fichiers physiques**, stockés sur la machine Windows qui héberge le serveur, séparément du code applicatif.

> Important : l'archive finale V1.25.13.17 n'est pas actuellement présente dans GitHub ni dans les fichiers accessibles à cet audit. Le dépôt contient un Manager récent, mais les sources serveur versionnées sont antérieures à la totalité des changements V1.25.13.x. Les éléments ci-dessous sont donc classés en « vérifié », « confirmé par exécution Windows » et « à récupérer depuis l'archive finale ».

## 1. Stockage physique vérifié

### 1.1 Base SQLite serveur

Chemin logique actuel :

```text
<data_dir>\club.sqlite3
```

Sous Windows, le lanceur construit ce chemin avec :

```text
GESTION_CLUB_DATA_DIR=<dossier programme>\data
GESTION_CLUB_DATA_PATH=%GESTION_CLUB_DATA_DIR%\club.sqlite3
```

Le journal d'exécution V1.25.13.15 confirme en environnement réel :

```text
D:\GestionClub\FC_LA_COUR_GestionClub\data\club.sqlite3
```

La base est explicitement conservée lors des mises à jour et les tests utilisent des bases temporaires.

### 1.2 Stockage navigateur

Le Manager conserve encore une base métier locale principale dans `localStorage` :

```text
gestionclub_full_proto_v100
```

Cette valeur contient l'objet `state` complet.

Autres clés `localStorage` identifiées :

- `gestionclub_coach_lineups`
- `gestionclub_portal_member`
- `gestionclub_coach_member`
- `gestionclub_coach_team`
- `gestionclub_before_restore_backup`

- `gestionclub_last_import_reset_backup`
- `gestionclub_before_demo_reset_backup`
- marqueur de migration/réinitialisation de données de référence.

### 1.3 IndexedDB navigateur

Une base IndexedDB de récupération existe :

```text
GESTION_CLUB_RECOVERY
```

Object store :

```text
backups
```

Elle est utilisée avant certaines écritures/restaurations sensibles pour conserver une copie récupérable.

### 1.4 Session navigateur

`sessionStorage` est utilisé pour des états temporaires, notamment :

- `gestionclub_admin_account`
- `gestionclub_stats_drilldown`
- diagnostics d'import FFF (`gestionclub_fff_import_diagnostics_v1`).

Ces données ne doivent pas être traitées comme une base métier persistante.

### 1.5 Logs Windows

Le runtime écrit également des fichiers techniques sous `logs\`, notamment :

- `dernier_serveur.log`
- `dernier_test.log`
- `derniere_mise_a_jour.log`
- logs d'erreur de tests datés selon les versions du lanceur.

Ces fichiers relèvent de l'exploitation, pas de la base métier.

- `watch_runs`

## 4. Flux réels de lecture / écriture

### 4.1 Mode navigateur / Manager

Lecture principale :

```text
localStorage['gestionclub_full_proto_v100'] -> state
```

Écriture principale :

```text
state -> JSON.stringify -> localStorage['gestionclub_full_proto_v100']
```

De nombreuses fonctions du Manager écrivent directement dans ce state local.

### 4.2 Sauvegarde serveur explicite

Flux actuel :

```text
state navigateur
 + lineups
 + feedback
 + scenarios
        |
        v
qaBackupPayload()
        |
        v
PUT /api/snapshot
        |
        +--> INSERT revisions(payload JSON complet)
        |
        +--> reconstruction table members
        |
        +--> reconstruction table teams
```

La sauvegarde serveur est donc aujourd'hui une **capture complète** et non une suite de transactions métier fines.

### 4.3 Lecture serveur

Le serveur expose notamment :

- état/révision courante ;
- historique des révisions ;
- téléchargement d'une révision complète ;
- résumé SQL ;
- liste/détail des licenciés ;
- liste/détail des équipes ;
- veille ;
- PDF ;
- convocations.

### 4.4 Restauration locale

La restauration du backup :

- remplace le `state` principal ;
- remplace les compositions ;
- remplace feedback/scénarios ;
- crée préalablement des sauvegardes de récupération dans `localStorage` et/ou IndexedDB selon le parcours.

## 5. Redondances actuellement identifiées

Les mêmes informations peuvent exister simultanément dans plusieurs emplacements :

### Licenciés

1. `localStorage` dans `state.members`
2. backup complet JSON
3. `revisions.payload` dans SQLite
4. table SQLite `members`
5. champ JSON `members.payload` de chaque ligne SQL

### Équipes

1. `localStorage` dans `state.teams`
2. backup complet JSON
3. `revisions.payload`
4. table SQLite `teams`
5. champ JSON `teams.payload`

### Comptes

Deux familles existent déjà conceptuellement :

- comptes présents dans `state.accounts` du Manager ;
- comptes d'authentification serveur stockés dans SQLite.

La V1.25.13.x a justement commencé à rapprocher les profils serveur et les portails. Cette jonction doit être reconstruite précisément depuis l'archive finale avant migration V1.26.

## 6. Risques architecturaux confirmés

### R1 — fichier physique unique

`club.sqlite3` contient actuellement authentification, sessions, snapshots complets, projections métier, veille, PDF binaires et convocations.

Conséquence : la sauvegarde/restauration est trop grossière et un incident sur ce fichier touche plusieurs domaines sans rapport direct.

### R2 — source de vérité ambiguë

Pour certains domaines, on ne peut pas encore dire simplement « cette table est la vérité » :

- le Manager modifie `localStorage` ;
- le serveur conserve un snapshot JSON ;
- certaines tables SQL sont seulement reconstruites depuis ce snapshot.

### R3 — duplication volumique

Chaque nouvelle révision ajoute un backup complet dans `revisions.payload`, même si une seule fiche a changé.

### R4 — PDF binaires dans SQLite

Les PDF de veille sont stockés comme BLOB dans `club.sqlite3`, ce qui augmente la taille et lie documents et données structurées dans un même fichier.

### R5 — multi-club insuffisamment structuré

La sauvegarde connaît une affiliation club, mais les tables métier actuelles ne sont pas structurées partout avec une clé `club_id` explicite.

### R6 — comptes/licences non canoniquement liés

Il existe encore une séparation entre comptes du Manager, comptes serveur, licenciés et rôles. La V1.26 devra définir les identifiants et liens stables.

### R7 — dépôt incomplet par rapport au runtime final

Les sources serveur actuellement dans GitHub sont antérieures à la totalité des modifications V1.25.13.x. Un journal Windows V1.25.13.15 montre un `server.py` nettement plus volumineux et des contrôles de profils absents de la copie GitHub actuelle.

**Aucune migration destructrice ne doit commencer tant que l'archive finale V1.25.13.17 n'a pas été réinjectée/figée comme source de référence.**

## Conclusion V1.26.0

L'objectif initial est confirmé : la V1.25.13.x fonctionne, mais son stockage est historiquement empilé.

Le principal fichier `club.sqlite3` mélange actuellement plusieurs responsabilités, tandis que le Manager conserve encore une base complète côté navigateur. La V1.26 doit donc **clarifier la source de vérité puis séparer physiquement les domaines**, en maintenant une migration non destructive depuis V1.25.13.17.
